# HARD-LLM-CHALLENGE: Инцидент в GPU-кластере

Ты — ведущий инженер по распределённым вычислениям, специалист по дискретной оптимизации и формальной верификации.

Тебе передан аварийный планировщик заданий вычислительного кластера. Его результаты неверны, а часть входных событий приходит с задержкой и дублируется.

Требуется восстановить правильное состояние системы, найти глобально оптимальное расписание, исправить реализацию, доказать корректность алгоритма и предоставить исполнимый код.

**Внимание:** эвристически хорошее расписание не считается решением. Нужно именно доказуемо оптимальное. Решение, нарушающее хотя бы одно жёсткое ограничение, считается ошибочным независимо от полученного значения целевой функции.

Запрещено использовать интернет, внешние API и готовые оптимизационные решатели. Разрешены Python 3.12, стандартная библиотека и выполнение собственных программ.

## Часть 1. Описание кластера

Есть четыре GPU:

- GPU0
- GPU1
- GPU2
- GPU3

Каждая GPU имеет 64 ГиБ VRAM, из которых 8 ГиБ постоянно зарезервированы системой.

Следовательно, для заданий доступно не более 56 ГиБ на каждой GPU.

Горизонт планирования состоит из восьми дискретных временных интервалов: 0, 1, 2, 3, 4, 5, 6, 7.

Каждое задание имеет фиксированный полуоткрытый интервал `[start, end)`.

Задание либо вообще не выполняется, либо целиком размещается на одной допустимой GPU на весь интервал. Миграции, деление задания и изменение времени запуска запрещены.

На одной GPU одновременно может находиться несколько заданий при соблюдении суммарного ограничения VRAM.

Общие лимиты кластера в каждом временном интервале:

- Суммарная мощность выполняющихся заданий не более 750 Вт.
- Суммарная нагрузка на PCIe не более 38 условных единиц.

Мощность и PCIe-нагрузка являются глобальными: от выбранного номера GPU они не меняются.

Простой GPU не создаёт дополнительной мощности или PCIe-нагрузки. Постоянные системные расходы уже учтены отдельно и не входят в указанные лимиты.

## Часть 3. Журнал событий

Изначально все задания активны и имеют параметры из таблицы.

Параметры могут изменяться событиями. Отчёт строится по времени `ingested_at`, а не `occurred_at`.

Время в формате UTC. Во всех событиях дата 2026-10-12.

| event_id | job | field | value | revision | occurred_at | ingested_at |
|---|---|---|---|---:|---|---|
| E01 | J07 | profit | 110 | 1 | 11:30 | 11:58 |
| E02 | J03 | enabled | false | 1 | 11:59 | 12:06 |
| E03 | J13 | allowed | [1,2] | 1 | 11:50 | 12:07 |
| E04 | J05 | profit | 90 | 1 | 12:02 | 12:03 |
| E04 | J05 | profit | 90 | 1 | 12:02 | 12:03 |
| E05 | J17 | enabled | false | 1 | 11:20 | 11:40 |
| E06 | J17 | enabled | true | 2 | 11:25 | 12:11 |
| E07 | J02 | profit | 95 | 1 | 11:35 | 12:00 |
| E08 | J08 | allowed | [0,1,3] | 1 | 11:55 | 12:12 |
| E09 | J12 | profit | 120 | 1 | 09:00 | 12:09 |
| E10 | J14 | profit | 130 | 1 | 11:45 | 12:10 |

Правила восстановления событий:

1. `event_id` является глобальным идентификатором.
2. Абсолютно одинаковые повторные записи с тем же `event_id` учитываются один раз.
3. Если две записи имеют одинаковый `event_id`, но отличаются хотя бы одним полем, восстановление должно завершаться явной ошибкой, а не выбирать произвольную запись.
4. Для каждого сочетания `(job, field)` используется событие с наибольшим `revision` среди доступных на момент снимка.
5. Два разных события с одинаковыми `(job, field, revision)`, но разными значениями — конфликт; его необходимо обнаруживать.
6. Перестановка записей журнала не может менять результат.
7. Отсутствие события означает использование исходного параметра.
8. `ingested_at <= cutoff` включительно.
9. Изменения распространяются только на указанные поля.
10. При восстановлении исторического снимка запрещено использовать будущие события.

Построй два независимых снимка:

- S1: `2026-10-12T12:00:00Z`
- S2: `2026-10-12T12:10:00Z`

Снимки оптимизируются независимо друг от друга. Стоимости переноса заданий между S1 и S2 не существует.

## Часть 4. Целевая функция

Для каждого снимка нужно найти допустимое расписание.

Порядок оптимизации строго лексикографический:

1. Максимизировать сумму `profit` выбранных заданий.
2. При равенстве прибыли максимизировать количество выбранных заданий.
3. При равенстве первых двух показателей минимизировать максимальную суммарную мощность в каком-либо временном интервале.
4. При полном равенстве выбрать лексикографически минимальный вектор размещения.

Вектор размещения строится в порядке J01, J02, ..., J18.

Каждая позиция содержит номер GPU от 0 до 3, либо число 4, если задание не выбрано.

Например:

`[0, 4, 2, ...]`

означает J01 на GPU0, J02 не выбрано, J03 на GPU2.

Никакие дополнительные критерии оптимизации использовать нельзя.

## Часть 5. Неисправный код

Ниже фрагмент существующего планировщика:

```python
def schedule(jobs, events, cutoff):
    active = {j["id"]: j for j in jobs}

    for event in events:
        if event["occurred_at"] > cutoff:
            continue

        job = event["job"]

        if event["field"] == "enabled":
            if not event["value"]:
                active.pop(job, None)
        else:
            active[job][event["field"]] = event["value"]

    available = list(active.values())

    available.sort(
        key=lambda j: j["profit"] /
        (j["mem"] * (j["end"] - j["start"])),
        reverse=True
    )

    result = {}
    used = [[0] * 8 for _ in range(4)]

    for job in available:
        for gpu in job["allowed"]:
            if all(
                used[gpu][t] + job["mem"] < 64
                for t in range(job["start"], job["end"])
            ):
                result[job["id"]] = gpu

                for t in range(job["start"], job["end"]):
                    used[gpu][t] += job["mem"]

                break

    return result
```
