# Экспертное испытание LLM: аудит финансового движка

Ты выступаешь в роли principal software engineer, финансового аудитора и архитектора баз данных. Тебе передана неисправная система расчётов маркетплейса.

Задача — провести расследование, восстановить точные денежные результаты, исправить реализацию и доказать, что она корректна.

**Запрещено:** использовать приблизительную арифметику, игнорировать неудобные события, менять бизнес-правила, считать неполные результаты правильными или ссылаться на отсутствующие данные, если решение выводится из условий.

Ответ должен быть технически строгим. Все деньги выражаются целым количеством копеек.

## 1. Правила системы

1. Каждый заказ состоит из товарных строк. `quantity` — количество единиц.
2. Скидка на заказ распределяется между товарными строками пропорционально стоимости строк до скидки. Используй метод наибольших остатков: целые копейки сначала распределяются вниз, затем оставшиеся копейки выдаются строкам с наибольшими дробными остатками. При равенстве остатков раньше получает строка с лексикографически меньшим `line_id`.
3. Скидка строки распределяется по отдельным единицам товара тем же методом. При равенстве остатков раньше получает единица с меньшим порядковым номером.
4. Возврат конкретной единицы уменьшает выручку ровно на её стоимость после скидки. Одна единица не может быть возвращена дважды.
5. Комиссия маркетплейса — 12% от оставшейся выручки заказа.
6. Резерв удержаний — 10% от оставшейся выручки заказа.
7. Комиссия и резерв округляются до целой копейки методом ROUND_HALF_UP **отдельно для каждого заказа**.
8. Логистика начисляется один раз на отгруженный заказ и при возврате не компенсируется.
9. Штрафы вычитаются из выплаты и не уменьшают базу комиссии и резерва.
10. Выплата = оставшаяся выручка − комиссия − резерв − логистика − штрафы.
11. Отчёт на момент `cutoff` учитывает только события с `ingested_at <= cutoff`, независимо от `occurred_at`.
12. События имеют глобальный уникальный `event_id`; повторное получение того же события не меняет расчёт.
13. Итог не должен зависеть от порядка доставки событий. Состояние рассчитывается по множеству уникальных событий, доступных на момент отсечения.
14. Все времена — UTC.

## 3. Журнал событий

`occurred_at` и `ingested_at` приведены в формате `HH:MM` даты 2026-10-12 UTC.

| event_id | Тип | Заказ | Данные | occurred_at | ingested_at |
|---|---|---|---|---|---|
| e01 | SHIPPED | A | logistics=350 | 09:00 | 09:01 |
| e02 | SHIPPED | B | logistics=250 | 09:10 | 09:11 |
| e03 | SHIPPED | C | logistics=700 | 09:20 | 09:21 |
| e04 | PENALTY | A | amount=100 | 10:00 | 10:02 |
| e05 | REFUND | A | line=X, unit=1 | 11:00 | 11:55 |
| e05 | REFUND | A | line=X, unit=1 | 11:00 | 11:56 |
| e06 | REFUND | B | line=Z, unit=2 | 11:50 | 12:05 |

Дополнительно представь, что e02 поступило по сети трижды, но во всех копиях содержится один и тот же `event_id` и одинаковые данные.

Нужно рассчитать два независимых снимка:

- S1: `cutoff = 2026-10-12T12:00:00Z`
- S2: `cutoff = 2026-10-12T12:10:00Z`

## 4. Неисправная реализация

```python
def payout(order, events, cutoff):
    gross = sum(
        row["price"] * row["quantity"]
        for row in order["lines"]
    )

    total = gross - order["discount"]

    for event in events:
        if event["order_id"] != order["id"]:
            continue

        if event["occurred_at"] > cutoff:
            continue

        if event["type"] == "REFUND":
            line = next(
                x for x in order["lines"]
                if x["line_id"] == event["line_id"]
            )
            total -= line["price"]

        elif event["type"] == "SHIPPED":
            total -= event["logistics"]

        elif event["type"] == "PENALTY":
            total -= event["amount"]

    commission = round(total * 0.12)
    reserve = round(total * 0.10)

    return total - commission - reserve
```
