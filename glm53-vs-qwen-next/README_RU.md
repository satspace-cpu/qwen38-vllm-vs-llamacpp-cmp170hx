# GLM-5.3-Flash против Qwen3.8 Flash-Next FP8 / AWQ на 4× CMP 170HX

**Результаты 8 coding-agent задач — только правильность:** [сравнение GLM с Qwen FP8, AWQ и 27B](coding-8-tasks/RESULTS_RU.md). **Баллы из 80: FP8 79,5 · AWQ 78 · 27B BF16 77 · GLM 76.** Время GLM не сравнивается: во время теста сервер одновременно обрабатывал ещё два потока.

**Повтор 8 coding-agent задач на GLM:** [отдельные задания без решений и инструкция](coding-8-tasks/README_RU.md) · [все 8 условий одним файлом](coding-8-tasks/TASKS_ONLY_RU.md).
**Практический тест — 14 октября 2026.** [English version](README.md) · [Предыдущая статья AWQ против FP8](../flash-next-awq-vs-fp8/README_RU.md)

К прежнему сравнению двух квантов Qwen3.8 Flash-Next мы добавили **GLM-5.3-Flash AWQ W4A16 с отдельными W8-весами и MTP-Q8**, а также два сложных теста реального coding-agent: точный планировщик GPU и финансовый движок маркетплейса с SQL и регрессиями.

**Главное:** GLM обработала **499 403 входных токена и выдала 1024 выходных** за **93,506 с**. Скорость prefill — **5775,4 ток/с**, генерация — **145,4 ток/с**, TTFT — **86,470 с**. Оба сложных задания правильно решены по основным расчётам. В независимом повторном прогоне прошли **27/27 тестов планировщика** и **21/21 первоначальных Python-тестов финансового движка**. Позже мы нашли дефект, дали контрпример и проверили его исправление: **28/28 тестов**.

## Конфигурация сервера

| Компонент | Характеристики |
|---|---|
| GPU | 4× NVIDIA CMP 170HX (GA100/SM80), разблокировано по 64 ГиБ HBM2e, всего 256 ГиБ |
| Интерконнект | PCIe Gen2 ×16, одна NUMA, без NVLink |
| CPU и RAM | AMD EPYC 7F52 (16 ядер / 32 потока), 128 ГБ DDR4 |
| ПО | Debian, драйвер NVIDIA 610.57.04 |
| GLM модель | GLM-5.3-Flash-AWQ-W4A16-aggr-w8-mtpq8c-int4g32-mixA |
| GLM движок | Кастомный vLLM 0.1.dev20051+g487ecf187, PP=4, TP=1, деление слоёв 14/11/11/9 |
| GLM настройки | MTP4, KV BF16, max-model-len 524288, GPU utilization 0.91 |
| Qwen Next | SM80-патчи, TP4, MTP4; AWQ использует EP/Marlin; контекст 524288 через YaRN |

GLM запускалась **без Qwen-специфичных MRoPE/YaRN overrides**. Заявленная ёмкость KV cache при загрузке не является доказательством работы одного запроса на 1M.

## 1. Графики скорости

**Важно о честности сравнения:** Qwen FP8 и AWQ тестировались одним скриптом с точно заданным числом реальных входных токенов, уникальным префиксом и 512 выходными токенами. Новые GLM-прогоны использовали другой скрипт с повторяющимся синтетическим текстом, примерной длиной запроса и **1024 выходными токенами** на 303K и 499K. Также отличаются архитектура, параллелизм, CPU offload и kernels. Поэтому **графики не доказывают процентного ускорения GLM относительно Qwen в строго одинаковых условиях**. **GPU-планировщик:** 18 заданий, 4 GPU, ограничения VRAM/мощности/PCIe, зависимости, запреты и отложенные события для двух исторических снимков. Все три агента нашли точный оптимум **S1=811, S2=806**. Число тестов неодинаково, поэтому сравнивать только количество PASS некорректно.

**Финансовый тест:** точные копейки, скидки на товарные единицы, комиссии, резервы, возвраты, штрафы, историческое время событий, Python и PostgreSQL 16. **Оговорка по Qwen:** в исходных агентных архивах разные checkpoints использовали один и тот же API model ID. По одному JSON архива **нельзя уверенно приписать конкретную сессию именно FP8 или AWQ**, поэтому сессии честно помечены **A/B**. В одном архиве на ~52,9 минуты нет корректного завершающего маркера. Время включает инструменты, повторы и глубину проверки, то есть **не равно скорости вычисления токенов**.

## 3. Ошибка GLM и быстрый повторный тест

В финансовом коде GLM была реальная ошибка исторической воспроизводимости: конфликт дублей проверялся **до** отбора по ingested_at <= cutoff. Поэтому событие e05 с конфликтующей копией от 12:30 могло ломать старый отчёт за 12:00.

После предоставления этого контрпримера GLM обнаружила **3 падения (25/28 до исправления)**, изменила порядок обработки и получила **28/28 PASS**. Я независимо повторил проверку. Итоги S1/S2 не поменялись; при наличии обоих конфликтующих событий на дату запроса конфликт по-прежнему обнаруживается. На доработку ушло примерно **2 мин 13 с**.

**Остаточный риск:** Python выбрасывает ошибку для видимого конфликта, а SQL-версия записывает конфликт, но продолжает отдавать сумму. Это поведение перед реальным применением необходимо согласовать; независимого теста PostgreSQL в этой статье нет. Кроме того, на сервере GLM был виден каталог ранее полученного решения Qwen — нет доказательств, что модель использовала чужой код, но полной изоляции теста не было.

## Вывод и воспроизведение

GLM **реально обработала ~500K токенов** на четырёх CMP 170HX, решила оба технических задания по основным расчётам и быстро исправила регрессию после конкретного воспроизводимого контрпримера. Qwen Next AWQ остаётся очень быстрым вариантом генерации по предыдущему строгому парному тесту двух Qwen. **Ни один из этих результатов не доказывает всеобщее интеллектуальное превосходство какой-либо модели.**

Дальше нужны одинаковые задачи, скрытые тесты, одинаковый агентный бюджет и лимит токенов, чистые изолированные каталоги, проверка фактического checkpoint и несколько повторов. Для GLM дополнительно нужно измерить **качество извлечения фактов внутри 500K**, не только prefill.

В этой статье опубликованы проверяемые CSV, графики SVG, **полные оригинальные ТЗ двух задач** и использованный GLM benchmark script. Сырые ZIP сессий не загружаются в публичный репозиторий, так как могут содержать ненужную историю команд и локальные сведения о сервере.

В [старой статье](../flash-next-awq-vs-fp8/README_RU.md) остаются 8 более коротких coding-тестов: ручные оценки Qwen AWQ **78/80**, FP8 **79,5/80**, dense 27B BF16 **77/80** на двух GPU.
