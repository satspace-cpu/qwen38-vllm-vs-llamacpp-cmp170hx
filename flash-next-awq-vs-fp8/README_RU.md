# Qwen3.8: Flash-Next AWQ W4A16 против Flash-Next FP8 против Dense 27B на CMP 170HX — 520K + coding-agent

[English version](README.md) · [Python-скрипт теста](bench_vllm_512k_exact_mtp4.py) · [Задачи и эталонные решения](TASKS_AND_SOLUTIONS_RU.md) · [CSV long-context](benchmark_results.csv) · [CSV coding-agent](coding_agent_results.csv)

## Зачем проводился этот тест

Изначально это было практическое сравнение двух вариантов **одной и той же архитектуры Qwen3.8 Flash-Next** на необычном, но очень мощном локальном сервере с четырьмя разблокированными NVIDIA CMP 170HX. Затем к тем же восьми coding-agent задачам был добавлен третий прогон — **dense Qwen3.8-27B BF16 на 2× CMP 170HX**.

Цель была не просто получить красивые цифры на коротком промпте. Хотелось ответить на два вопроса, которые реально важны для локального coding/agent использования:

1. Как ведут себя **Flash-Next AWQ W4A16** и **Flash-Next FP8** от 15K до примерно 520K входного контекста?
2. Теряет ли значительно более быстрая 4-битная AWQ-модель столько качества в кодинге и reasoning, что выигрыш в скорости перестаёт иметь смысл?
3. Как на том же наборе coding-agent задач выглядит меньшая **dense Qwen3.8-27B BF16**?

На этой системе результат оказался очень наглядным: **AWQ W4A16 была примерно на 21% быстрее по cold prefill и примерно на 41% быстрее по генерации, а ручная проверка восьми coding-задач показала лишь небольшую разницу в качестве относительно FP8.** Dense **27B BF16** набрала **77/80**, то есть осталась близко по качеству. Её agent-сессия заняла **1 058 с**, но этот прогон был выполнен только на **2× CMP 170HX / TP=2**, тогда как оба Flash-Next прогона шли на **4× CMP 170HX**. Поэтому время 27B здесь — полезный двух-GPU baseline, **а не apples-to-apples сравнение скорости**.

Это не официальный бенчмарк модели и его нельзя автоматически переносить на другие GPU. Результат сильно зависит от железа и backend: AWQ здесь работала через WNA16/Marlin на SM80, тогда как FP8 использовала другой вычислительный путь.

## Конфигурации моделей

### FP8 — базовая точка сравнения

FP8 была уже отлаженной рабочей конфигурацией Flash-Next на этом сервере:

- 4 GPU и tensor parallel;
- MTP depth 4;
- YaRN-контекст до 524 288;
- BF16 KV cache;
- PLE/Engram CPU offload через `VLLM_PLE_CPU_OFFLOAD=1`;
- существующие SM80-патчи для Flash-Next FP8.

CPU-offload PLE/Engram оказался важным именно для FP8: при попытке оставить всю эту часть в GPU давление на память было заметно выше.

### AWQ W4A16

Использовался локальный checkpoint:

```text
Qwen3.8-Flash-Next-AWQ-W4A16
```

Рабочая конфигурация:

- TP=4;
- `--enable-expert-parallel`;
- 512 routed experts, по 128 локальных experts на каждую GPU;
- CompressedTensors WNA16 MoE;
- backend **Marlin WNA16**;
- MTP depth 4;
- YaRN-контекст 524 288;
- BF16 KV cache;
- `--engram-config.cpu_offload false`, то есть PLE/Engram остаётся в GPU.

Важная деталь: TP=4 без Expert Parallel не подходил этому AWQ checkpoint. После TP-разделения промежуточный размер MoE получался 160, а group size AWQ равен 128; статические scale-группы пересекали границы TP shard. Включение Expert Parallel решило эту проблему.

Отдельному AWQ fork также понадобился compatibility patch: model-wide `CompressedTensorsConfig` нельзя было ошибочно применять к PLE n-gram embedding, если сами PLE-веса checkpoint не хранятся в этом W4 формате.

Точная рабочая команда AWQ:

```bash
VLLM_ALLOW_LONG_MAX_MODEL_LEN=1 CUDA_VISIBLE_DEVICES=0,1,2,3 \
/mnt/llama-data/vllm-venv/vllm-0.31-qwen38-flash-next-awq-w4a16-sm80/bin/vllm serve \
/mnt/llama-data/modelsVLLM/Qwen3.8-Flash-Next-AWQ-W4A16/ \
--served-model-name Qwen3.8-Flash-Next-FP8 \
--host 0.0.0.0 \
--port 8000 \
--disable-access-log-for-endpoints /health,/-/health,/v1/models,/metrics \
--enable-auto-tool-choice \
--tool-call-parser qwen3_coder \
--reasoning-parser qwen3 \
--dtype bfloat16 \
--tokenizer-mode auto \
--gpu-memory-utilization 0.9 \
--tensor-parallel-size 4 \
--distributed-executor-backend mp \
--enable-expert-parallel \
--max-model-len 524288 \
--hf-overrides '{"text_config":{"rope_parameters":{"mrope_interleaved":true,"mrope_section":[11,11,10],"rope_type":"yarn","rope_theta":10000000,"partial_rotary_factor":0.25,"factor":2.0,"original_max_position_embeddings":262144}}}' \
--kv-cache-dtype bfloat16 \
--enable-prefix-caching \
--max-num-seqs 4 \
--max-num-batched-tokens 8192 \
--enable-chunked-prefill \
--scheduling-policy fcfs \
--async-scheduling \
--speculative-config '{"method":"mtp","num_speculative_tokens":4}' \
--attention-backend auto \
--load-format auto \
--engram-config.cpu_offload false
```

`served-model-name` специально оставлен таким же, как у FP8-профиля: локальные программы ожидают фиксированный API model ID. Это не означает, что AWQ checkpoint является FP8.

### Dense Qwen3.8-27B BF16

Третий coding-agent прогон выполнялся на **двух CMP 170HX** с dense checkpoint:

```text
/run/media/server/nvme/vllm_model/Qwen3.8-27B/
```

Конфигурация запуска:

- `CUDA_VISIBLE_DEVICES=0,3`;
- tensor parallel size 2;
- BF16 weights / activations;
- без квантизации (`quantization=None`);
- MTP с **5 speculative tokens**;
- родной контекст **262 144 токена** для этого coding-теста;
- BF16 KV cache;
- chunked prefill и prefix caching включены;
- `max_num_batched_tokens=8192`.

В логах vLLM архитектура определилась как `Qwen3_5ForConditionalGeneration`, а MTP-голова — как `Qwen3_5MTP`. Checkpoint размером 51.75 GiB занял примерно **26.16 GiB на GPU** при TP=2. vLLM сообщил около **32.12 GiB KV cache на карту** и суммарную ёмкость примерно **927 тыс. KV-токенов**, поэтому для одного запроса с 262K контекстом запас был большим.

27B пока добавлена только в **coding-agent сравнение качества и wall time**. Полный speed-run 27B до 512K/520K на момент этого обновления ещё не проводился.

## Методика скоростного теста

Тест проводился через OpenAI-compatible API vLLM с **точным cold prompt**.

Точный Python-скрипт теста добавлен в репозиторий: [bench_vllm_512k_exact_mtp4.py](bench_vllm_512k_exact_mtp4.py).

Он через `/tokenize` подбирает реальное число токенов и создаёт уникальный prefix для каждого прогона. Поэтому включённый на сервере prefix cache не превращает длинный тест в искусственный hot-cache результат.

Длинные точки:

```text
15K, 64K, 128K, 262K, 400K, 500K, 520K
```

На каждой генерировалось по 512 токенов. Дополнительно был отдельный тест: короткий prompt в 119 токенов и генерация 10 000 токенов.

`Effective prefill = prompt_tokens / TTFT`, поэтому метрика включает API/scheduling/first-token overhead. Её правильно использовать здесь как **A/B-сравнение двух одинаковых прогонов**, а не как абсолютную замену чистой kernel-скорости prefill.

## Почему AWQ здесь настолько быстрая

Этот результат нельзя сводить к формуле «4 бита всегда быстрее FP8». На этой системе удачно сложилось сразу несколько факторов:

1. **Routed expert weights намного компактнее.** INT4 weight-only снижает объём чтения expert-матриц из HBM.
2. **Expert Parallel хорошо подходит архитектуре.** 512 experts распределяются по четырём GPU, вместо неудобного разрезания W4-групп через TP.
3. **Marlin WNA16 — сильный путь для SM80.** На Ampere этот backend оказался очень эффективным.
4. **PLE/Engram в рабочей AWQ-конфигурации остаётся в GPU.** Сжатые experts освобождают под это заметно больше памяти.
5. **FP8 на CMP 170HX не является нативным Hopper FP8.** Поэтому его производительность сильнее зависит от software kernels.

То есть выигрыш даёт весь стек: **checkpoint format + vLLM kernels + EP layout + SM80 + размещение PLE**.

## Проверка качества кодинга

Все **три конфигурации** получили одинаковые восемь задач в отдельных новых turn/session контекстах.

Набор покрывал:

1. Python session grouping, сортировку и граничные условия;
2. AsyncCache, race condition, in-flight sharing и cancellation;
3. минимальный покрывающий диапазон по множеству отсортированных списков;
4. PostgreSQL: агрегации, последний заказ, индексы;
5. строгий TypeScript parser порта;
6. multi-file Python storage с нормализацией и защитой внутренних объектов;
7. LRU + TTL с требованием амортизированного O(1);
8. bounded-concurrency async runner с отменой и большим генератором jobs.

Полные условия и эталонные решения: [TASKS_AND_SOLUTIONS_RU.md](TASKS_AND_SOLUTIONS_RU.md).

### Ручная оценка качества

Это ручная оценка корректности и соблюдения ТЗ, а не официальный benchmark score.

| Задача | AWQ W4A16 | FP8 | Dense 27B BF16 | Наблюдение |
|---|---:|---:|---:|---|
| 1. Session grouping | 9.5 | **10.0** | **10.0** | Все решили правильно; у 27B и FP8 чуть чище объяснение |
| 2. AsyncCache | **10.0** | **10.0** | **10.0** | Все хорошо обработали shared work, retry и cancellation |
| 3. Covering range | **10.0** | **10.0** | **10.0** | Корректный heap, O(N log K) |
| 4. PostgreSQL | 9.5 | 9.5 | **10.0** | У 27B получился особенно аккуратный SQL |
| 5. TypeScript parser | **10.0** | **10.0** | **10.0** | Все выполнили строгий контракт |
| 6. Storage semantics | 9.5 | **10.0** | **10.0** | AWQ дополнительно сделала `strip()` email — этого не было в ТЗ |
| 7. TTL/LRU | **10.0** | **10.0** | **7.5** | 27B связала очистку expiry с LRU-порядком и пропустила контрпример |
| 8. Async runner | 9.5 | **10.0** | 9.5 | FP8 аккуратнее всех обработала тонкий случай `CancelledError` |
| **Итого** | **78.0 / 80** | **79.5 / 80** | **77.0 / 80** | Все три близки, но у 27B есть одна реальная логическая ошибка в задаче 7 |

Главное здесь не сам небольшой разброс баллов. **AWQ не провалила ни одной из восьми задач**, а dense 27B тоже осталась близко по общему качеству, но на задаче 7 проявилась содержательная логическая ошибка. В её LRU/TTL реализации порядок lazy-expiry был связан с LRU-порядком: протухший MRU-элемент мог остаться в cache, пока свежий LRU-элемент удалялся. Это хороший пример решения, которое выглядит убедительно, но не выполняет весь контракт.

## Время выполнения coding-agent сессии

По timestamp в журналах получилось:

| Задача | AWQ W4A16 | FP8 | Dense 27B BF16 |
|---|---:|---:|---:|
| 1 | **15.3 с** | 33.8 с | 36.7 с |
| 2 | **46.9 с** | 59.1 с | 71.4 с |
| 3 | **35.0 с** | 47.4 с | 130.8 с |
| 4 | **34.6 с** | 43.1 с | 69.8 с |
| 5 | **28.8 с** | 47.3 с | 82.1 с |
| 6 | **22.8 с** | 30.1 с | 59.4 с |
| 7 | **60.5 с** | 81.6 с | 170.7 с |
| 8 | **71.4 с** | 82.7 с | 437.2 с |
| **Всего** | **315.2 с** | **425.1 с** | **1 058.1 с** |

AWQ завершила весь набор примерно за **5 мин 15 с**, FP8 — примерно за **7 мин 05 с**, а dense 27B TP2 — примерно за **17 мин 38 с**. Но время 27B нужно трактовать отдельно: она работала только на **2 GPU / TP=2**, в то время как AWQ и FP8 использовали **4 GPU**. Поэтому отношения времени к AWQ/FP8 приведены как наблюдение, но не являются честным same-hardware рейтингом скорости.

Это agent-level результат: он включает и сырую скорость генерации, и то, сколько reasoning/tool шагов потребовалось модели. Особенно много итераций у 27B было на задачах 7 и 8.

## Практический вывод

На этом конкретном сервере 4× CMP 170HX **Qwen3.8 Flash-Next AWQ W4A16 сейчас выглядит лучшей основной рабочей конфигурацией**:

- около **+21% cold-prefill** на диапазоне 15K–520K;
- около **+41% decode** на том же диапазоне;
- около **+43%** в тесте генерации 10K токенов;
- около **26% меньше wall time** в coding-agent тесте из восьми задач;
- при этом небольшая разница в ручной оценке качества относительно FP8: **78/80 против 79.5/80**;
- текущий dense 27B прогон даёт полезный **двух-GPU TP2 baseline**: **77/80 за 1 058 с**, но для прямого сравнения эффективности с Flash-Next нужен повтор тех же восьми задач на **4× CMP 170HX / TP=4**.

FP8 при этом остаётся полезной как **контрольная конфигурация максимальной надёжности** для особенно сложных задач, где даже небольшая потеря reasoning из-за квантизации может иметь значение. Dense 27B остаётся интересной как более компактная двух-GPU база. Её результат по качеству уже полезен, а сравнение wall time нужно считать предварительным до повторного прогона на **4× CMP 170HX / TP=4**.

Следующий действительно полезный этап — не ещё один синтетический speed test, а большой repo-level coding benchmark: несколько файлов, скрытые регрессии, запуск тестов, архитектурные изменения и длинный контекст проекта. Именно там небольшая потеря качества W4, если она есть, должна проявиться заметнее всего.

## Важные замечания

- API model ID специально оставлялся одинаковым для обоих профилей из-за совместимости с локальными программами.
- Prefix cache на сервере включён, но exact-cold script использует уникальный prefix для каждой длинной точки.
- YaRN: `factor=2.0`, `original_max_position_embeddings=262144`, `max_model_len=524288`.
- Flash-Next AWQ/FP8: MTP с 4 speculative tokens. Текущий dense 27B TP2 coding-прогон использовал 5 speculative tokens; для будущего TP4 повтора лучше выставить тот же MTP depth, что и у Flash-Next, чтобы сравнение времени было чище.
- Это результаты **одного локального запроса**, а не серверный multi-user throughput.
- Между версиями vLLM kernel selection может существенно измениться, поэтому точную конфигурацию важно фиксировать вместе с цифрами.
