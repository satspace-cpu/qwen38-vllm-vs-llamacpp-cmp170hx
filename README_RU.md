# Qwen3.8-27B: vLLM против llama.cpp на 2× CMP 170HX 64 ГБ

[English version](README.md)

## О проекте

Здесь собираются реальные тесты **Qwen3.8-27B BF16** на двух NVIDIA CMP 170HX, разблокированных до 64 ГБ каждая. Сравниваются **vLLM** и **llama.cpp** с упором на длинный контекст и реальную работу кодинг-агентов.

Нас интересуют не только красивые цифры на коротком запросе, а то, что происходит при 100K, 150K, 200K и 250K+ токенов контекста: скорость префилла, скорость генерации ответа, MTP/speculative decoding и распределение модели между GPU.

> Репозиторий будет дополняться. Ниже находятся уже измеренные результаты на одной и той же тестовой системе.

## Тестовая система

| Компонент | Конфигурация |
|---|---|
| GPU | 2× NVIDIA CMP 170HX, разблокированы до 64 ГБ |
| Power Limit | до 300 Вт на карту |
| CPU | 2× Xeon E5-2697 v4 |
| Модель | Qwen3.8-27B BF16 |
| Максимальный контекст | 262 144 токена |
| Параллельных запросов | 1 |
| vLLM | Tensor Parallel + MTP/speculative decoding |
| llama.cpp | CUDA, layer/tensor split, BF16 KV cache |

## Главное сравнение около 260K

| Движок / режим | Prompt | Префилл | Генерация | MTP acceptance |
|---|---:|---:|---:|---:|
| vLLM + MTP | 250 000 | ~1 200 tok/s по TTFT | ~20.7 tok/s по TPOT | **77.0%** |
| llama.cpp Layer + MTP | 260 052 | **835.6 tok/s** | **31.6 tok/s** | 36.4% |
| llama.cpp Tensor + MTP | 260 052 | **705.5 tok/s** | **37.7 tok/s** | — |
| llama.cpp Tensor без MTP | 260 052 | **825.9 tok/s** | **26.1 tok/s** | — |

## vLLM — тест 250K + 2048

Результат `vllm bench serve`:

```text
Total input tokens:       250000
Total generated tokens:   2048
Benchmark duration:       306.97 s
Output throughput:        6.67 tok/s
Total token throughput:   821.08 tok/s
TTFT:                     208313.69 ms
TPOT:                     48.20 ms/token

MTP acceptance rate:      77.02%
Acceptance length:        4.85
Draft tokens:             2115
Accepted tokens:          1629
```

Здесь есть важный нюанс. **6.67 tok/s — это не чистая скорость генерации после префилла.** Эта цифра усреднена по всему запросу вместе с огромным 250K-префиллом.

По `TPOT = 48.20 ms/token` чистый decode получается примерно:

```text
1000 / 48.20 ≈ 20.75 tok/s
```

Именно эту цифру логичнее сравнивать с `eval time` llama.cpp.

## llama.cpp — Layer + MTP

Финальный лог:

```text
prompt eval time = 311200.27 ms / 260052 tokens
                 = 835.64 tokens/s

eval time        = 13087.51 ms / 414 tokens
                 = 31.56 tokens/s

draft acceptance = 0.36351
                 = 269 accepted / 740 generated
mean len          = 2.82
```

Во время самой генерации скорость постепенно росла:

```text
101 tokens → 27.25 tok/s
192 tokens → 28.61 tok/s
294 tokens → 30.09 tok/s
400 tokens → 31.12 tok/s

последние 3 секунды около 400 токенов → 34.36 tok/s
```

То есть даже почти у потолка 262K модель продолжает выдавать порядка **30–34 tok/s**.

## llama.cpp — Tensor + MTP

```text
prompt eval time = 368599.88 ms / 260052 tokens
                 = 705.51 tokens/s

eval time        = 7800.06 ms / 295 tokens
                 = 37.69 tokens/s
```

Получилась интересная картина:

**Tensor медленнее Layer на префилле, зато быстрее генерирует ответ.**

При этом в логе есть важные предупреждения:

```text
backend sampling not supported with SPLIT_MODE_TENSOR; using CPU
spec ... backend offload failed ... using CPU sampler
```

Поэтому Tensor-режим ещё нужно отдельно исследовать: часть sampling/speculative-механики уходит на CPU.

## llama.cpp — Tensor без MTP

При отключении MTP сервер пишет про `blk.64... unused tensor`. Это нормально: MTP-слой физически находится внутри модели, но мы его не используем.

```text
prompt eval time = 314871.81 ms / 260052 tokens
                 = 825.90 tokens/s

eval time        = 10694.55 ms / 280 tokens
                 = 26.09 tokens/s

graphs reused    = 278
```

Получаем очень наглядное сравнение Tensor:

| Tensor | Prefill | Generation |
|---|---:|---:|
| без MTP | **825.9** | 26.1 |
| с MTP | 705.5 | **37.7** |

То есть в этом тесте MTP дал примерно **+44% к скорости генерации**, но одновременно ухудшил префилл примерно на **15%**.

Значение vLLM здесь приблизительное: `250000 / TTFT`. TTFT включает не только чистый model prefill, поэтому в следующих тестах этот показатель будем измерять ещё аккуратнее.

## Первые выводы

**Layer в llama.cpp очень хорош для огромного префилла.** На 260K он показал 835.6 tok/s и заметно обошёл Tensor+MTP.

**Tensor интереснее для скорости ответа.** 37.7 tok/s на практически полном 262K контексте — хороший результат.

**MTP действительно работает.** В Tensor-тесте генерация выросла с 26.1 до 37.7 tok/s.

**Но реализация MTP сильно отличается между движками.** vLLM в нашем тесте получил около **77% acceptance**, тогда как llama.cpp Layer — только **36%**.

**vLLM визуально значительно ровнее нагружает GPU.** Во время тестов нагрузка и питание двух CMP 170HX держались заметно стабильнее. В llama.cpp мощность карт могла резко гулять примерно от десятков ватт до лимита. Пока это наблюдение, а не отдельный количественный тест — позже добавим телеметрию.

И главное: **короткий benchmark совершенно не показывает поведения движка при реальной агентской работе на 150–260K контекста.** Именно поэтому мы и собираем эту серию тестов.

## Команда теста vLLM

```bash
vllm bench serve \
  --backend openai \
  --base-url http://127.0.0.1:8000 \
  --model /mnt/llama-data/modelsVLLM/Qwen3.8-27B \
  --dataset-name random \
  --input-len 250000 \
  --output-len 2048 \
  --num-prompts 1 \
  --max-concurrency 1 \
  --temperature 0
```

## Что тестируем дальше

Будем строить единую таблицу от маленького до максимального контекста:


Для каждой точки фиксируем **реальные prompt tokens**, **prefill tok/s**, **generated tokens**, **generation tok/s**, **TTFT**, **MTP acceptance**, распределение нагрузки между GPU и режим Layer/Tensor.

Отдельно сравним MTP ON/OFF и посмотрим, в какой точке контекста vLLM и llama.cpp начинают резко терять скорость генерации.

## Зачем всё это

Обычные benchmark'и часто измеряют короткие запросы. Для кодинг-агента это мало что значит. Агент начинает с нескольких тысяч токенов, затем читает проект, историю диалога и файлы — и легко доходит до 100K–250K.

Именно там становится видно, какой движок реально удобнее для многочасовой работы.

**Продолжение следует — новые замеры будут добавляться сюда.**
